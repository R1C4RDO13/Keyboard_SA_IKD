01 · Project Context

The assignment, the choice, the goal

The work was structured around the practical-work assignment for academic year 2025/2026. Three early decisions shaped everything that followed.

🎓

Academic context

Practical-work deliverable for Trabalho prático 2025/2026. The project ran one full academic semester, with the roadmap acting as the operating system of the work — each phase reviewed locally before the next was started.

🔱

Why fork Fossify Keyboard

Building a keyboard and a research pipeline and a dashboard from scratch was not realistic in one semester. Fossify Keyboard provided a modern, privacy-focused, well-architected Kotlin codebase. The project could focus on the research questions instead of the keyboard engine.

🔬

Research, not product

The deliverable is a working prototype, not a finished consumer app. It demonstrates a complete capture → storage → analysis → visualisation pipeline. Phases 10 (rebrand), 12 (mood-curated emoji drawer) and 13 (persistent mood bar) have since shipped; only Phase 14 (gamification badges) remains documented as a plan — the academic value lies in the pipeline itself.

05 · Phase Walk-through

How the work evolved

Each phase had explicit frozen surfaces, an explicit reopened-files list, and an explicit verification recipe. The plans evolved during implementation — Phase 5 exists because Phase 4's on-device review surfaced a UX gap. This is the operating-system property of the roadmap.

Foundation — sensor calibration & live keyboard alignment

Build trust in the measurements before risking the live keyboard.

A standalone DiagnosticsActivity was created with a real-time view of inter-key delay, key hold time, flight time, and live gyroscope/accelerometer read-outs. The screen surfaced numerics and animated bars side-by-side so any timing math error would be immediately visible.

Phase 1.1 moved the validated capture out of the diagnostic screen into the live keyboard. The capture site is the top of SimpleKeyboardIME.onKey(), off the main thread — the constraint that has held the input-latency budget through every later phase.

Metric definitions were also realigned in 1.1. Dwell was reframed to Key Hold Time; flight became the precise UP→DOWN interval; IKD remained the legacy UP→UP interval for historical comparison. Diagnostic, live, database — all three layers now agree on what each number means.

Persistent local storage & privacy mode

Persist the captured signals to disk without compromising battery, latency, or privacy.

The Room database ikd.db was introduced with three tables: sessions, ikd_events, sensor_samples. A write-behind buffer (LiveCaptureSessionStore) batches events to disk every 500 ms or every 100 events, via a single Executors.newSingleThreadScheduledExecutor().

Privacy mode is the default — no rows are written until the user explicitly toggles capture on (later via the keyboard top-bar shield, then via the Phase 8 mood bar). A SAF-based dual-block CSV export rounds out the phase. Sensor sampling is gated on session activity — sensors come up with the keyboard and stop immediately on close.

A periodic retention CoroutineWorker runs once per day with the setRequiresBatteryNotLow constraint. Users can choose a retention window; the default is "forever".

Translate raw on-device data into something a user can read.

Session detail — metadata header to real dashboard

Make the per-session detail screen useful at a glance, then turn it into a real dashboard.

Phase 4 added a metadata header card to EventFeedActivity when launched with a session id: started, duration, orientation, locale, counts, and four derived metrics (WPM, error rate, avg IKD, avg dwell, avg flight). Powered by one additive getSessionStats(sessionId) query that folds counts and averages in a single SQL round-trip.

The sensor list switched from a wall of X / Y / Z numbers to a single magnitude per sample, with a toolbar toggle to flip back to per-axis view. Magnitude is computed in Kotlin at read time — never stored, never in the CSV. The data contract stays frozen.

Phase 5 replaced the raw timing/sensor row dump with a KPI strip + three line charts (IKD over time, gyro magnitude over time, accel magnitude over time). SQL-side downsampling guarantees ≤ 200 points per chart regardless of session length, with bucket width max(50 ms, ceil(durationMs / 200)).

The live mode of EventFeedActivity (launched from Diagnostics → "View Log", without a session id) keeps its raw timing and sensor lists — that screen is a real-time debug feed and a different feature.

Capture closure — emoji + autocorrect + weighted error rate

Close two capture blind spots — emoji palette taps and external text replacements.

This was the first phase since Phase 2 to deliberately reopen the keyboard layer. Every edit is instrumentation-only:

  • Emoji palette taps now route through a new OnKeyboardActionListener.onEmojiText and are recorded as EMOJI events.
  • External replacements (system spell-check, VN Telex inline transliteration) are detected via an onUpdateSelection heuristic — cursor moved by an unexpected amount, outside a 50 ms grace window of our last IME edit — and recorded as AUTOCORRECT events.

Phase 7.1 upgraded the error-rate metric. A new correction_weight column on ikd_events (Migration(2, 3)) lets a single autocorrect of a long misspelled word contribute proportional weight to the error rate, instead of the same "1" a single backspace contributes. The user's ocasdasda → october test case correctly reads ~90% error rate after this change (was misleadingly ~9%).

The CSV gained a trailing correction_weight column on the timing block — strictly additive, parsers reading the original seven columns ignore the eighth.

Mood bar & contextual overlay

Let the user annotate their emotional state with a single keyboard tap.

The keyboard top bar gained a seven-button mood bar — 🛡️ 😊 😲 🤢 😢 😨 😠 — covering the privacy shield (preserved verbatim from Phase 2) plus Ekman's six basic emotions, valence-ordered. Tapping a mood writes a MoodEntry row keyed on the active session via the new Migration(1, 2).

The bar evolved through five sub-phases:

  • 8.1 — sizing, dashboard card theming, toggleable mood bar visibility (Config.showMoodBar).
  • 8.2 — every slot became a true two-way toggle. The bar was redressed as a stretched-key capsule with a chat-bubble PopupWindow for first-person feedback ("I'm feeling happy", "I want privacy"), replacing the original toasts.
  • 8.3 — dropped the "Avg Mood" KPI and the "Mood over Time" line chart, since averaging across categorical labels produced interpretively vague numbers like 🤢 3.2. Replaced them with a per-bucket stacked-bar mood-mix chart showing the percentage breakdown of each Ekman category over time.
  • 8.4 — a short pop + wiggle "dance" animation (plus the existing keyboard haptic) plays when the user selects a slot; deselect taps stay silent.
  • 8.5 — the bar became a collapsible, right-anchored chip that remembers the user's standing self-rating across sessions via a display-only Config.lastMoodScore (no auto-write to mood_entries) and auto-clears it after one hour of inactivity. The chip expands to the full seven-slot row on tap and auto-collapses after a selection.

The error-rate metric was also corrected post-Phase 8: first by excluding BACKSPACE from the denominator (569f331b), then by dropping AUTOCORRECT from the formula entirely (303e792f) — the IME-level autocorrect heuristic can't reliably distinguish a true spell-check accept from spell-check noise across OEMs, so AUTOCORRECT rows are still captured (CSV, event log) but no longer feed the error-rate KPI / chart / live cell. "Correction" now means BACKSPACE only.

Privacy invariant preserved: MoodEntry stores only the integer ordinal valence (1..6) and a timestamp. No emoji codepoint, no text. The score → emoji mapping lives in helpers/MoodEmoji.kt only.

Rebrand to moodScript

Retire the "Fossify Keyboard" identity now that the app has evolved into a behavioural-analytics platform.

Cosmetic-only scope. No applicationId rename, no ikd.db migration, no fastlane / store metadata work, no colorPrimary change, no schema migration. The smallest change set that gives the app a coherent on-device identity: name, About screen, launcher foreground glyph.

The launcher glyph is the original Fossify keyboard silhouette (rounded rectangle outline + 5×2 dot keys + spacebar pill, white on background) cradled by three concentric heart outlines fading outward. Both brand pillars — keyboard + wellbeing — in one mark.

Mood at the input layer — curated emoji drawer + persistent mood bar

Make the user's standing mood actually change what the keyboard offers, not just what the dashboard records.

Phase 12 — mood-curated emoji section. When the user opens the keyboard's emoji drawer and a standing mood is set (Config.lastMoodScore != SCORE_NONE), a context-aware section is prepended at the top of the emoji list with ~15–25 curated emojis for that mood (e.g. Mood: 😊 → 😄 😁 🥰 ✨ 🌈 🎉 …). When no mood is set the drawer renders unchanged. Reuses Phase 7's onEmojiText capture pipeline, so the DB still stores only eventCategory = "EMOJI" — never the codepoint. The per-mood curated lists live in helpers/MoodEmoji.kt only.

Phase 13 — persistent right-anchored mood bar. The mood bar moved from the leading edge to the trailing edge and is lifted into an overlay layer above both the regular keyboard toolbar and the emoji drawer, so the user can swap their mood without closing the drawer — which immediately re-curates the Phase 12 section (via the existing OnSharedPreferenceChangeListener path in SimpleKeyboardIME). The bar keeps every Phase 8.2 / 8.4 / 8.5 behaviour — collapsible chip, dance animation, chat-bubble feedback, standing rating — it's purely a re-position + re-layer. No new capture-path code, no schema change, no DAO touch.

Phase 14 — gamification: badges (planned)

The one remaining planned phase. Reward consistent mood cataloging and keyboard usage with a starter set of ~13 badges, surfaced as a new sixth "Achievements" tab.

Would add a new badges table via Migration(3, 4) (the third migration) — six mood-cataloging badges + seven keyboard-usage badges, evaluated lazily on dashboard open, with an in-app snackbar on first unlock and no system notifications. Badges are derived from existing tables only, so the privacy posture is unchanged and the CSV gains no badges block. (The plan was originally drafted as "Phase 13"; that slot was claimed by the right-anchored-mood-bar feature, so the gamification work is renumbered to 14.)

08 · What's next

The pipeline is the deliverable

Phases 10 (rebrand), 12 (mood-curated emoji drawer) and 13 (persistent mood bar) have all shipped. Phase 14 (gamification badges) is the one phase still documented as a plan. The academic value of the project is the capture / storage / analysis / visualisation pipeline itself — not any particular surface built on top of it.

🎨

Phase 10 — Rebrand Shipped

The "Fossify Keyboard" identity was retired in favour of MoodScript: new launcher glyph (keyboard cradled by three hearts), new About screen, new app name. Cosmetic only — no schema migration, no applicationId rename (that, plus store metadata, is deferred to a release-readiness pass).

🎭

Phase 12 / 13 — Mood at the input layer Shipped

Phase 12 adds a context-aware curated emoji section at the top of the emoji drawer when a standing mood is set. Phase 13 moves the mood bar to the trailing edge and overlays it above both the keyboard toolbar and the emoji drawer, so changing mood mid-drawer re-curates the section immediately. Reuses the Phase 7 emoji-capture pipeline; no new privacy surface.

🏆

Phase 14 — Gamification Planned

~13 starter badges across mood cataloging and keyboard usage, surfaced as a new sixth "Achievements" tab on the dashboard. Migration(3, 4) adds a badges table; in-app snackbar on unlock; no system notification permission; badges derived from existing tables so the privacy posture is unchanged.
